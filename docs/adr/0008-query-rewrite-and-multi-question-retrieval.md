# ADR-0008：Query Rewrite 与多问题检索基线

- 状态：Accepted
- 日期：2026-08-27
- 修订：[ADR-0005](0005-streaming-rag-api.md) 的阶段与 Trace 契约
- 后续修订：[ADR-0010](0010-retrieval-post-processing-baseline.md) 已用加权 RRF 和有界去重
  替换本 ADR 的临时候选合并规则。

## 背景

M4-A 已让最近对话和历史摘要进入最终回答 Prompt，但检索仍只使用用户当前一句话。带有“它”、
“上一条”等指代的问题可能缺少独立语义；一个请求同时包含多个问题时，单条向量查询也容易遗漏
其中一部分。M4-B 需要在不进入 Intent、Rerank、正式融合算法或完整 RAG Pipeline 优化的前提下，
先建立可观察、可降级的 Query Rewrite 与多问题检索连接层。

## 决策

### 1. 严格结构化改写

复用 fast Chat 模型，根据当前问题、最近完整对话和可选历史摘要生成严格 JSON：

```json
{
  "rewritten_question": "可独立理解的问题",
  "sub_questions": ["用于检索的子问题"]
}
```

只接受这两个字段、非空字符串和 1～3 个不重复子问题；不接受 Markdown 代码块或模型附加说明。
改写只解析上下文指代并拆分问题，不回答问题，也不得改变用户意图。对话内容通过明确的数据边界
放入 Prompt，视为不可信输入。

### 2. 参数与降级

默认改写超时为 20 秒、最大输出为 512 token、最多 3 个子问题。这三个值都是可配置的工程安全
基线：20 秒限制 fast 模型故障对 120 秒全局预算的占用；512 token 足够承载短 JSON 且限制成本；
3 个子问题将单次检索放大控制在三倍以内。它们尚未经过效果评测，不代表最优参数。

模型超时、已知供应商错误或结构化输出不合规时，不中断问答，而是降级为原问题及唯一的原问题
子查询。降级原因使用稳定、无输入内容的代码写入日志和 Trace。未知编程错误仍向上抛出，避免
静默掩盖缺陷。改写和其后的所有步骤继续受现有 RAG 全局截止时间约束。

### 3. 并发检索与临时合并

每个子问题都使用相同知识库作用域并发执行向量检索；调用结束、失败、超时或取消时必须收拢或
取消全部子任务。所有结果按 Chunk UUID 去重，对重复 Chunk 保留“单个子查询中的最好名次，
其次最高相似度”的候选，再按该规则稳定排序并重新编号。

该算法只是 M4-B 的确定性最小合并基线，不是 RRF，也不声称已经优化相关性。M5 将通过评测选择
并替换候选融合与 Rerank 策略。多个结果必须报告一致的索引配置，否则按检索配置错误失败。

### 4. 可观察性与边界

Pipeline 增加 `rewriting` 阶段；该阶段 Trace 的 `candidate_count` 表示实际参与检索的子问题数。
Trace 增加可选 `degradation_reason`，正常成功时为空。公开 SSE 只暴露阶段和稳定降级代码，不暴露
原问题、改写文本、Prompt、会话正文或模型原始输出。会话消息和 RAG Run 沿用现有表，因此无需
数据库迁移。

本阶段不实现 Intent 分类、澄清交互、HyDE、关键词检索、RRF、Rerank、Embedding 调整或效果
评测结论。

## 备选方案

### 改写失败即终止请求

契约更严格，但会让辅助能力故障直接破坏原本可工作的单问题 RAG。保留原问题检索能提供更好的
可用性，同时通过 Trace 明确标记质量降级。

### 只使用改写后的单问题检索

实现更简单，但无法满足多问题实际参与召回的目标，也无法为后续融合评测建立候选基线。

### 本阶段直接使用 RRF 或 Rerank

可能改善排序，但会提前引入需要离线评测和参数选择的 M5 决策。当前先保留可解释的最好名次
合并，让后续算法能够和稳定基线比较。

## 后果

- 上下文相关问题可以在检索前补全指代，多问题可以并发参与召回。
- 最坏情况下每个请求产生三次向量查询，因此部署者需要结合数据库容量调整该上限。
- fast 模型故障不会自动导致整个问答失败，但调用方能从 Trace 识别降级。
- SSE 增加阶段枚举和可选 Trace 字段；兼容客户端应继续忽略未知字段与未来未知阶段。
- 排序只是临时基线，进入 M5 前不得把它描述为正式融合或相关性优化结论。
